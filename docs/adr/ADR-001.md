## 1. Context

The semester prototype connects an employee's support ticket to support work and related software bugs. Its requirements make a status change more than saving a new value. Resolving a ticket requires an authorized Support user and a public resolution note. Reopening it requires its owning Requester and a reason. Marking a bug Fixed requires its assigned Developer; verification belongs to Support. Closing a bug must leave linked tickets unchanged.

The same operation may also change several stored records. A ticket status change and its history must succeed together or leave neither change behind. Account disabling must not orphan In Progress work. These rules cross request handling, users, tickets, bugs, and history. The team needs one predictable place to implement and review each operation before separate members build those workflows.

The assignment places the decision inside a Django project. Django provides persistence tools, but our team still needs to choose where these project-specific rules live. The repository baseline contains requirements and working agreements; this ADR does not claim that an application implementation already exists.

The decision must balance:

- **Correctness:** the role matrix, ownership rules, lifecycle guards, and history requirements must apply even when someone sends a direct request instead of using the screen.
- **Testability:** the team must test valid and rejected operations, including data/history failures, without duplicating each rule in multiple request handlers.
- **Semester effort:** four members need a small, understandable structure. The charter does not require distributed services, external integrations, or a replaceable database abstraction.
- **Maintainability:** a change to a workflow should have one obvious implementation location, while simple data definitions remain easy to find.

## 2. Decision proposed for acceptance

**Place application workflow operations in explicit shared Python service functions inside the Django application. Views call those functions; services check business permissions and workflow rules, use the Django ORM directly, and save related data/history in one transaction.**

Here, a service is an ordinary Python function in the same application, not a separately deployed server. Proposed names such as `resolve_ticket`, `reopen_ticket`, `assign_bug`, and `verify_bug` illustrate the boundary; they are not claims that code exists or a commitment to final module names.

### Responsibilities and boundaries

| Part | Responsibility under this proposal |
| --- | --- |
| Views and forms | Handle HTTP/session/CSRF concerns, parse inputs, call the named operation, and translate its result or error into the user response. Forms may give early feedback but are not the only validation boundary. |
| Workflow services | Receive the server-authenticated actor and record IDs, load current relevant data, enforce role/ownership/state/input rules, and coordinate writes and required history. Never trust a client-supplied actor, role, prior status, or permission flag. |
| Models and database constraints | Define fields, relationships, and applicable data invariants. Supporting model methods are allowed, but a workflow's orchestration and actor-dependent policy have one service entry point. |
| Shared access/query helpers | Apply T2 visibility filters and permitted projections to reads, searches, and counts. They can be reused by services and views; write-service checks alone do not secure reads. |

All application paths that mutate governed ticket/bug/account workflows must call the relevant service. Operational Django admin edits must be disabled/read-only or explicitly routed through the same service; a generic save path must not bypass the policy. Controlled synthetic fixture loading may construct baseline records directly, but cannot stand in for tests of real user operations. This does not claim protection against an operator with unrestricted database access.

Each operation that changes business data and history uses an explicit `transaction.atomic()` block on the same database connection. Let a database failure escape that block before turning it into a user error. Append the required history inside the transaction, not in a later best-effort step. Explicit transactions provide the proposed rollback boundary; they do not by themselves prevent competing concurrent updates. Implementation review must choose and test database-appropriate locking or conditional updates where concurrent writes could violate an existing invariant.

We will not introduce a generic repository interface, signal-driven workflow orchestration, or a separate service deployment for this decision. Services use the ORM directly. This ADR does not choose the database engine, authentication provider, final Django app split, or framework version, and it does not alter the role matrix or add lifecycle states.

### Concrete example: resolve a ticket

1. A view obtains the authenticated actor and passes the ticket ID and resolution note to the resolution service.
2. The service checks the actor's current active Support role, the ticket's current state (Triaged or In Progress), and T2's nonblank note rules. Unauthorized callers receive no protected ticket information.
3. Inside the operation's transaction, it persists the public resolution note, changes status to Resolved, and appends the required status history with actor/time and old/new values. Any other FR12-covered fields changed by an operation receive their own required events.
4. If validation or authorization fails, nothing changes. If the history write fails after the data write, the transaction rolls the operation back. The response reports failure; it does not announce a successful resolution.

The service does not close linked bugs or tickets as a side effect. Reading the result still follows T2's access rules.

## 3. Alternatives and proposed reasons for not choosing them

The options below are genuine implementation choices assessed by the assistant for discussion. No member is claimed to have advocated or rejected an option yet. Record actual preferences and revise this comparison before acceptance.

| Option | Why it is a reasonable choice | Tradeoff and proposed reason not to choose it |
| --- | --- | --- |
| **A. Put workflow rules in views/forms** | Fewer layers; a developer can follow the HTTP request and its checks in one place. Appropriate when an operation is small and has one entry point. | Ticket and bug operations combine authorization, state, history, and account guards. Repeating them across handlers or admin paths risks inconsistent checks. A shared service makes the intended reusable operation explicit; the extra boundary is justified by these requirements. |
| **B. Put workflow orchestration on model methods/managers** | Behavior stays near its data, and methods can be tested independently of HTTP. Model methods can accept an actor and use transactions; this option can meet the requirements. | Account disabling, ticket/bug links, and history span several models. Choosing which model owns orchestration becomes less obvious and may create dependencies between them. We propose services as the explicit coordinator, accepting an extra module rather than concentrating cross-model workflows on one model. |
| **C. Shared workflow services using the ORM directly — proposed choice** | Gives every business operation a named entry point for permission checks, state rules, transactions, and history, callable without an HTTP request. | More functions and boundaries to learn; it works only if reviewers prevent bypasses and duplicated rules. We judge that cost proportionate to the existing cross-record requirements. |

The comparison is about where orchestration belongs, not whether models may contain any behavior. Neither rejected option is technically incapable of supporting authorization or transactions.

## 4. Consequences

### What becomes easier

- Reviewers can inspect one named operation for its permission, lifecycle, and history rules. Views become shorter and focus on handling requests.
- Tests can exercise service behavior directly, then use request-level tests to verify authentication, response visibility, and the mapping of errors.
- The data/history transaction boundary is explicit. Fault-injection tests can check the precise partial-write risk described by NFR02.

These are expected benefits, not measurements or proven implementation results.

### What becomes harder or remains a risk

- Even small changes may touch a form/view, a service, and tests. The team must learn when validation belongs at each boundary and avoid conflicting copies of business rules.
- Direct ORM updates, admin actions, or future scripts could bypass services. Reviews must inspect new write paths; service placement is a convention, not automatic enforcement.
- Cross-model operations can create module dependency cycles. Keep orchestration dependencies explicit; revisit boundaries if services repeatedly call one another in cycles.
- Transaction boundaries, concurrent updates, and database failure behavior need integration tests on the selected database. A successful mocked unit test is insufficient.
- Services remain coupled to Django's ORM and transaction facilities. Replacing persistence would require changes; we accept this because the charter does not promise database portability.
- Centralizing write operations does not make read endpoints safe. Visibility filtering, developer projections, and public/private history still need their own T2 tests.

### Planned verification and revisit trigger

Implementation evidence is future work. For the first implemented workflow, test: an authorized transition; a disallowed role/owner; an invalid source state; missing required text; expected history; and an injected failure between data and history writes. At request level, verify that direct-ID requests and every exposed alternative write path obey the same rules. Exercise concurrent attempts where they could break an ownership/state invariant. These checks refine how to verify T2, not a claim of passed tests.

Revisit this decision at the first sprint review after that workflow is implemented. Caleb, as the charter's proposed application/data owner, should bring the evidence and obtain team acknowledgement of that responsibility. Reconsider if the implementation repeats a rule across entry points, cannot express a required atomic operation cleanly, or the team finds the added structure costs more than it saves.
